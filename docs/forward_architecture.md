# Архитектура: вперёд-модель + функция ценности

## Почему не табличный ДП

Настоящий Invoker — десять способностей с независимыми кулдаунами и свободным
порядком кастов. Состояние есть вектор независимых счётчиков:

```
прямое произведение кулдаунов Invoker  : 8.25e11
произведение вместе с Pudge           : 1.62e17
```

Достижимость не спасает — BFS от состояния «всё готово»:

```
шаг 0:      638 векторов
шаг 1:   50 007
шаг 2:  986 518
шаг 3: 9 516 821      (за 0.9 с боя, и растёт дальше)
```

Кастовать можно любое подмножество готового в любой момент, поэтому достижимое
множество почти совпадает по порядку с произведением. Табуляция исключена
структурно, а не по стоимости железа.

**Это установленный отрицательный результат.** Он же снимает главное
ограничение: раз табуляции нет, размерность состояния больше не важна. Значит
возвращается настоящая двумерная арена 30×80 с условием поражения за выход,
которого в редуцированной модели не было вовсе.

## Архитектура

```
    ┌──────────────────────────────────────────────┐
    │  вперёд-модель (точные правила)              │
    │  dota2sim/sim.py + data/abilities_741f.py    │
    │  позиции в плоскости, 10 способностей,       │
    │  настоящие кулдауны, касты, задержки,        │
    │  снаряды, каналы, типы урона                 │
    └───────────────────┬──────────────────────────┘
                        │ состояние
                        ▼
    ┌──────────────────────────────────────────────┐
    │  поиск на каждом шаге 0.3 с                  │
    │  матричная игра по совместным действиям,     │
    │  ограниченная глубина, лист = оценка         │
    └───────────────────┬──────────────────────────┘
                        │ лист
                        ▼
    ┌──────────────────────────────────────────────┐
    │  функция ценности V(признаки)                │
    │  начальное приближение — редуцированный ДП,  │
    │  уточнение — подгонка по самопгре            │
    └──────────────────────────────────────────────┘
```

Это архитектура AlphaZero: точные правила в симуляторе, приближённая оценка в
листе. Не компромисс, а стандартный метод там, где табуляция невозможна.

## Что делать

1. **Достроить вперёд-модель** на `data/abilities_741f.py`: все 10 способностей
   Invoker с кастами, задержками, снарядами и типами урона; 4 способности
   Pudge; предметы из `data/items.py`; двумерная арена 30×80 с поражением за
   выход.

2. **Функция ценности.** Начальное приближение — таблица из редуцированного ДП
   (`solvers/npdp.solve_game_np_ordered`), как функция от (расстояние, запас
   места, HP, мана, кулдауны, бафы). Уточнение — подгонка по самопгре.

3. **Поиск.** На каждом шаге 0.3 с — матричная игра по совместным действиям
   (`solvers/matrixgame.py` уже есть) с ограниченной глубиной.

4. **Проверка поиска на малых точных случаях.** Критично: у меня уже есть
   табулируемые конфигурации, где ДП даёт строгий ответ (тест с двумя
   способностями — 629 тыс. состояний, 31 свип, секунды). Поиск обязан
   воспроизвести эти ответы, прежде чем ему можно верить на полной модели.

## Пойманные ошибки, которые нельзя повторять

Модель уже четырежды давала вырожденные результаты, и каждый раз причина была
в допущении, вшитом в конструкцию:

* **усреднённый кулдаун** вместо настоящих — и я выдал его за корректные
  кулдауны;
* **«оптимально кастовать всё готовое разом»** — вшито в форму урона, из-за
  чего ДП физически не мог выбрать иначе. Проверка показала, что это неверно:
  ДП выбирает Cold Snap отдельно, а Sun Strike по свободной цели наказывается
  (V 0.92 против 0.41);
* **квантование HP** стирало весь непрерывный урон;
* **одномерная геометрия** удалила угол и условие выхода из арены.

Правило: любое утверждение о стратегии — результат прогона, а не предпосылка
модели. И проверять, что модель воспроизводит статику, до прогона, а не после.
